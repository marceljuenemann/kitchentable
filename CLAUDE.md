# Kitchen Table

Open-source, non-profit dating app for London's ENM (ethically non-monogamous) community. Self-funded, run via the founder's Ltd for now, with a possible future CIC if it expands beyond London ENM.

Full product context — mission, principles, business model, MVP scope — lives in [PRODUCT.md](PRODUCT.md). Read it before making product decisions.

## Tech stack

- **Backend:** Supabase (Postgres, Auth via magic link, Storage). Schema/migrations in `supabase/migrations/`, pgTAP tests in `supabase/tests/database/`. Clients access `profiles` only through stored procedures, not tables/RLS — see [docs/database.md](docs/database.md) (profile statuses, transitions, access rules); keep it updated with schema changes. Photo handling (sizes, storage layout, privacy) is in [docs/photos.md](docs/photos.md). The sign-in email is `supabase/templates/magic_link.html` (email-safe HTML: tables, inline styles, hex colours), wired up in `config.toml` for both the Magic Link and Confirm signup templates so they stay identical; keep the sign-in button the first link (e2e reads the first `href`). Changes need `supabase stop && supabase start` to apply locally. Its logo is `web/public/email/logo-v1.png`, loaded via `{{ .SiteURL }}`; PNG rather than SVG because Gmail and Outlook don't render SVG, and never edit it in place (sent emails point at the URL; add `logo-v2.png` instead).
- **Frontend:** Angular (standalone components + signals, no NgModules) + Angular Material, in `web/`. Material 3 theme generated from the brand palette (`web/src/theme-colors.scss`) plus `--kt-*` tokens and the brand fonts ("Baloo Bhaijaan 2" + "Nunito Sans") in `web/src/styles.scss`; the design specs are in `prototype/onboarding/` and `prototype/browse/` (search grid, profile, Reach out). Link previews (WhatsApp etc.) come from the Open Graph tags in `web/src/index.html` and `web/public/og-image-v1.png` (1200×630, loaded from the production URL); like the email logo, never edit it in place, add `og-image-v2.png`.
- **Local dev:** see [README.md](README.md) for setup. `supabase start` for the backend, `ng serve` for the frontend, Mailpit for magic-link emails. Keep both `supabase start` and `ng serve` running in the background rather than starting/stopping them per task — the user keeps them running too and is happy to share the same instance to preview changes live.

## Status

Sign-up (invite code + magic link) and sign-in are built. Invite codes are not validated: requesting a link always succeeds and creates the account if needed, so the forms never reveal whether an address is registered (keep it that way: no "no such user" or "invalid invite" messages). The code from the `?invite=` link is stored in the sign-up metadata, copied into `profiles.vetting_answers` (as `invite_code`) on submission and checked by hand during vetting. Passwords are disabled by a trigger on `auth.users` that never stores one (see "No passwords" in [docs/database.md](docs/database.md)). Signed-in users land on `/app`, a shell that shows a screen based on their profile status: terms not accepted → the terms screen (`features/terms/`: the Terms of Use and the Privacy Policy's explicit consent as two separate checkboxes, inserted into `terms_acceptances`, which clients use directly under RLS; the sign-up form has no checkbox, so agreeing happens only once the address is confirmed), no profile row → onboarding, `vetting` → "being vetted", `approved` → age verification, `active`/`disabled`/`admin` → main app. Each screen includes the shared `app-header`/`app-footer` components as needed (the main app won't use the footer). Onboarding has its infrastructure (draft store, stepper) and steps 1 ("Create profile"), 2 ("About you") and 3 ("Add photos": picking, cropping, upload to the `photos` bucket, display from storage, and drag-to-reorder with the first photo as the main one) and 4 ("Vetting": two private questions, 80 characters minimum each, then optional feedback on onboarding stored as `onboarding_feedback`; the answers live in the draft as `vettingAnswers`) built. "Submit application" calls `ProfileService.submitOnboarding()` (the `submit_onboarding` procedure creates the row in `vetting`) and reloads the profile, which makes the shell show "being vetted" (`onboarding/submitted/`: "Thanks for applying!", plus a card saying we launch at 100 sign-ups with the applicant's personal invite link to share or copy, `app-invite-link` in `shared/invite-link/`, also at the end of search; the code is a hash of their user id, see "Signup and invite codes" in [docs/database.md](docs/database.md)). Once approved, applicants verify their age with Didit (`features/age-verification/`, shared heading styles `.kt-status-heading` in `styles.scss`): the `start-age-verification` edge function creates a Didit session and the app redirects to Didit's page; Didit's signed webhook (`didit-webhook`) calls `complete_age_verification`, which makes the profile `active` and sets `age_verified_at`; Didit sends the user back to `/app?status=…`, which is only a hint for the screen (after `Approved` it polls with `ProfileService.fetchStatus()` until the webhook has landed). Locally there's no Didit API key and Didit can't reach the webhook, so e2e signs fake webhooks (`e2e/support/didit.ts`, secret in `supabase/functions/.env`). See "Age verification" in [docs/database.md](docs/database.md), which also lists the Didit console settings. The main app (`features/main/`) has the bottom nav from `prototype/browse/` (Your profile, Search, Connections, Messages, Community; the prototype's "Likes" is renamed Connections) and a `<router-outlet>` for its tabs, which are child routes of `/app` (`MAIN_ROUTES` in `main.routes.ts`, loaded with the shell from `signed-in-chunk.ts`): Search is `/app` itself, the others `/app/profile`, `/app/connections`, `/app/messages` and `/app/community`. The shell still decides by status, so the tabs only show for members whose status shows the main app. Search (`features/main/search/`, from `prototype/browse/`) is built against **mock data** for now (`mock-members.ts`: made-up members with drawn SVG photos; anything mock is marked `MOCK:`): `SearchStore` (provided on the route, so filters survive tab switches) filters, sorts and hides in memory. For real, the server will return only the profiles the caller may see (`search_profiles()`, which exists but isn't called yet: same location, not connected or dismissed, and `hide_by_gender` both ways; see [docs/database.md](docs/database.md)), and filtering and sorting will stay in the browser while members are few. It has the filter bar (Looking for, Gender, Age: `FilterSheetComponent`, a bottom sheet from the onboarding option lists: chips for Looking for and Gender, each plus Self-described for anything people wrote themselves (and Gender's Not specified for an empty gender), and under Gender a `.kt-switch-row` "Only show me to these genders" (`SearchStore.hideByGender`, saved as `profiles.hide_by_gender` but not applied to anyone yet); a two-thumb slider for Age that applies while dragging (`input` events, not `valueChange`), with a switch "Include profiles with no age" (on by default; off leaves them out at any age too). Filters apply live and are saved on the profile with `set_search_filters`, fire-and-forget with a Retry snackbar on failure, so they survive signing out; Clear clears the open one and closes the sheet), newest members first (by `age_verified_at`, the only order for now), always ending with "That's everyone for now" and the member's invite link (no separate empty state: the list is short anyway), swipe-left-to-hide on the grid (`hideable` on `app-profile-grid`) with an Undo snackbar (`.kt-snackbar`), and other people's profiles over the grid at `/app/profiles/:id` (`SearchProfileComponent`, a child of the Search route like `/admin/vetting/:id`, where the bottom nav keeps Search as the current tab: `MainComponent.currentTab`) with a bottom bar of two equal buttons, "Hide profile" (the accessible alternative to swiping) and Reach out, which only says it isn't ready yet. The search page is `position: fixed` and scrolls itself, so while a profile shows it raises itself over the bottom nav. Connections (`connections/`) will list incoming connection requests only (not the ones you sent); until introductions exist it's always its empty state: the header, a panda holding the logo's heart (`HugPandaComponent`, an inline SVG button: tapping it hugs the heart and sends hearts in the logo's colours floating up, which only fade with reduced motion; a "Tap me!" hint with an arrow sits diagonally above it until the first hug), then "No connection requests" (no "yet": it also shows once you've dismissed them all) and a line on what will show up there. Tabs with no visible title of their own (Search, Connections) have a `.kt-visually-hidden` `h1` for screen readers. The other tabs are "under construction" placeholders (`UnderConstructionComponent`: the title from the route's `data` and a `.kt-notice`); the profile tab (`profile-tab/`) adds the account card with sign-out and the legal links, since the main app has no footer. The Terms of Use and Privacy Policy are Markdown in `docs/policies/`, bundled into the app as strings (the `.md` loader in `web/angular.json`) and rendered with `marked` by `app-policy` (`shared/policy/`), which has no page layout so it can also go in a sheet (`openPolicySheet()`, which loads the documents only when opened). They're public at `/about/terms` and `/about/privacy`, linked from the footer. There's one version of each (0.1), which can be edited freely until production; after that, old versions are to be kept viewable (not built yet). Analytics are first-party: `AnalyticsService.track()` calls the `track_event` procedure, which writes to `analytics_events` (event names allowlisted, kept for 3 months, no third party, nothing stored in the browser). Onboarding records `onboarding_step_viewed`. See `analytics_events` in [docs/database.md](docs/database.md) for what may be recorded. The onboarding draft lives in localStorage via `UserStorage` (`core/user-storage.ts`: keys scoped to the user id, survives session expiry, cleared only on explicit sign-out: every "Sign out" must use `injectSignOut()` (`core/auth/sign-out.ts`), which calls `UserStorage.onSignOut()` before ending the session, never `AuthService.signOut()` directly), and a profile row is created only on submission. Admins are separate accounts with a profile in status `admin` (inserted by hand in Studio): they use the app like members but are never shown to them. The admin tool is under `/admin` (`features/admin/`), behind `adminGuard` (a `canMatch` guard calling `is_admin()`, which sends members to `/app`). It's in the same lazy chunk as the shell (`features/signed-in-chunk.ts`), because the two share code that would otherwise become a third chunk onboarding users fetch one round trip later; its backend is the `admin_*` procedures and admin read access to photos (see "Admins" in [docs/database.md](docs/database.md)). `/admin/vetting` shows the applications as the grid members will browse (`VettingStore` loads them whole, in one request); `/admin/vetting/:id` is a child route that opens one over the grid as the member-facing profile plus a vetting box (tagline, invite code, answers, onboarding feedback, and Approve, which closes the profile and takes it off the grid). The grid and profile are shared with search (`shared/profile-grid/`, `shared/profile-view/`, built from the `prototype/browse/` handoff): opening and closing morphs the tile's photo into the profile's with the View Transitions API (`withViewTransitions()` in `app.config.ts`, skipped for every other navigation; see `profile-transition.ts`), and the grid page scrolls in its own container because the router scrolls the window to the top on every navigation. Emails other than sign-in go through one edge function, `send-email` (`supabase/functions/`), with no personal data: triggers on `profiles` call `send_email(template, user_id)`, which posts to it via `pg_net`, and it sends through Mailtrap, or Mailpit locally. A new application emails the admin a link to `/admin/vetting`, and an approval emails the applicant a link to `/app` for the age check. The templates are in the function, as HTML in the sign-in email's style (`send-email/layout.ts`, a copy of `supabase/templates/magic_link.html`'s layout: keep the two in step) plus plain text. See "Emails" in [docs/database.md](docs/database.md). Edge functions only pick up new functions and `supabase/functions/.env` changes on `supabase stop && supabase start`.

The database side of connections and messages exists (`connections`, `connection_secrets`, `messages`, select-only under RLS, and `send_intro`, `accept_intro`, `decline_intro`, `send_message`, `end_connection`, `mark_read`, `set_dismissed`, `get_connected_profiles`), including every member's conversation with the admins: an accepted connection with each admin account, created when their profile goes live (see "Conversations with the admins" in [docs/database.md](docs/database.md)). No app code uses it yet.

Not built yet: real data for search (calling `search_profiles()` from `SearchStore`, members' photos readable by other members, saving dismissals with `set_dismissed`), the app side of connections/intros (the Reach out sheet), messaging in the app (planned to use RxDB for offline-tolerant messaging specifically; the sync and message emails are in [docs/database.md](docs/database.md), marked "planned").

## Working with the user

- **Edit files with the Edit/Write tools**, not through Bash (sed, Python, heredocs). They need no approval and are easier to review. This includes multi-file changes: do them one file at a time.
- **Don't commit or push unless asked.**
- **Restarting Supabase is fine when a change needs it** (`supabase stop && supabase start`, which keeps the local data, for example after editing `config.toml`, email templates or edge functions). Never `supabase stop --no-backup` or `db reset`. Don't stop or restart `ng serve`: if that's really needed (for example Vite's "Outdated Optimize Dep" 504 after installing a dependency), ask the user to do it.
- **Keep docs current in the same change:** update `docs/database.md`, `docs/photos.md` and this file when behaviour, schema or conventions change. Check plans and docs for stale numbers or wording before presenting them.
- **Schema changes go in a new migration** after the init one (the user's preference, and the init was only ever clean-slated while nothing existed). Apply it to the running local database with `npx supabase migration up --local` rather than `db reset`, which wipes the user's local accounts and drafts; `npx supabase test db --local supabase/tests/database` runs in rolled-back transactions and is safe.
- **Plan before big or unclear work.** When asked to plan ("just planning, no coding"), don't write code. Give a recommendation with the reasoning rather than a survey of options. Don't claim things about the code or database without checking (query the DB, read the file).
- **Keep it lean:** prefer the smallest thing that works (few stored procedures, no speculative columns, no extra tables). The user reviews the Supabase and security-relevant code closely, so keep that part small and clear.
- **Report honestly:** say what was verified and how (unit, e2e, screenshots) and what wasn't (for example real-phone touch).

## Frontend conventions

- **Look and feel is iterated with the user in small steps.** Match the existing look (brand fonts, colours, chips, sheets) and keep styles consistent across screens. Put repeated styling (labels, placeholders, chips, textareas) in `web/src/styles.scss` as global styles instead of per-component copies.
- **Pickers are bottom sheets** (`MatBottomSheet`, panelClass `kt-bottom-sheet`), not dialogs. Use `autoFocus: 'dialog'` so no button is focused on open.
- **No third-party requests for assets:** fonts and the icon font are self-hosted from npm packages (`@fontsource/*`, `material-icons`), listed under `styles` in `web/angular.json`. Don't load anything from Google Fonts or other CDNs: it sends visitors' IP addresses to them.
- **Form fields:** `floatLabel="always"` with a visible placeholder. Colours follow the theme tokens (`--mat-sys-*`, `--kt-*`) rather than hard-coded values.
- **State and storage:** signals for component state; the current profile comes from `ProfileService.state$` (rxjs). Anything user-scoped that lives in the browser goes through `UserStorage`. Don't add unrelated cross-service dependencies (avoid circular injection; prefer an explicit call, like `onSignOut()`).
- **Chunks:** few and big, to keep round trips down (see the comment in `app.routes.ts`). Signed-out pages go in the initial bundle, everything behind sign-in (the shell and the admin tool) is one lazy chunk (`features/signed-in-chunk.ts`), and only rarely opened heavy things (the policy documents with `marked`) load on demand. Don't add `@defer` or dynamic imports for small things. When the main app grows big (browse, messaging, RxDB), give it its own chunk so onboarding users don't download it.
- **Prefer a small library for hard gestures** (for example `@panzoom/panzoom`) and the Angular CDK for drag and drop, over hand-rolled code.

## Testing

- **Backend (pgTAP):** `supabase/tests/database/`. Run via `npx supabase db reset && npx supabase test db --local supabase/tests/database`. Run after any migration, RLS policy, or trigger change.
- **E2E (Playwright):** `e2e/`, config at `playwright.config.ts`. Covers invite/auth flows and the status-driven shell — landing-page invite gating, the sign-in bottom sheet, auth-guard redirects, and which screen each profile status shows (fixtures in `e2e/support/admin.ts` create users/profiles via the service role). Run via `npx playwright test` from the repo root — needs `supabase start` running (Playwright starts `ng serve` itself if it isn't already running). Run the relevant spec(s) after changes under `web/src/app/core/auth/`, `web/src/app/features/landing/`, or `web/src/app/features/auth-callback/`, `web/src/app/features/shell/`; run the full suite (`npx playwright test`) for anything broader or route/guard-related.
- **Unit tests (Karma + Jasmine):** `*.spec.ts` next to the code under `web/src/app/`, config in `web/karma.conf.js`. `npm run test:unit` from the repo root runs them once in headless Chrome (`npm test` in `web/` watches in a real Chrome window). They need no Docker or Supabase: services get fakes for `SupabaseService`, `AuthService` and `UserStorage` (see `profile.service.spec.ts`, `onboarding-draft.store.spec.ts`), and components are tested through their signals and DOM. Cover logic (validation gates, mapping, state transitions, error paths); don't test trivial templates or Material itself, and leave user journeys to Playwright. Add or update specs with the code they cover.
- **Checks (format, lint, types, build, unit tests):** `npm run check` from the repo root runs Prettier `--check`, `ng lint` (angular-eslint), a type-check of `e2e/`, a production `ng build` and the unit tests — it needs no Docker and is quick. Run it (or at least `npm run format:check` / `npm run lint`) after changes under `web/` or `e2e/`; fix formatting with `npm run format`.
- CI (`.github/workflows/ci.yml`) runs two parallel jobs on every push to `main` and every PR, always in full regardless of what changed locally: `check` (the checks above, including the unit tests) and `e2e` (`supabase db lint`, pgTAP, Playwright). On `main`, a third job, `deploy-staging`, then deploys to staging (migrations, auth config and email templates, edge functions, frontend), and `deploy-production` waits for manual approval and deploys the same commit to production. Both run the reusable `.github/workflows/deploy.yml`: see "Staging" and "Production" in [README.md](README.md). `main` is always meant to be releasable; unfinished work stays on a branch or behind a flag. Merged migrations reach staging right away, so never edit one after merging; add a new one. Changes to `[remotes.staging]` in `supabase/config.toml` usually belong in `[remotes.production]` too.

- **Photos e2e** (`e2e/photos.spec.ts`) covers crop, upload, persistence, failure and retry, and mouse and emulated-touch reordering. Real-device touch isn't covered. When adding tests that interact with a bottom sheet, wait for its animation to settle before dragging. The `expect` timeout is 15 s because the first visit to a lazy chunk compiles on the cold dev server.
- Run pgTAP and `npx supabase db lint --local --schema public --fail-on error` after schema changes. Don't call `require_auth_uid()` inside a `where` clause (lint complains); assign it to a variable first.

Known Angular/Material gotchas hit while building this (worth knowing before repeating them):
- Field initializers that reference an injected dependency must use `inject()`, not constructor-parameter properties — constructor param properties are assigned *after* field initializers run, so `readonly form = this.fb.group(...)` with `constructor(private fb: FormBuilder)` throws "used before initialization."
- Don't set a `mat-stepper`'s initial step via `@ViewChild` + imperative `selectedIndex =` after render — `CdkStepper`'s own content-init logic runs after that and silently overwrites it. Bind `[selectedIndex]` from the template instead, computed before the stepper exists.
- supabase-js can deadlock if you call it synchronously from inside an auth state change callback. `AuthService.userId$` uses `observeOn(asyncScheduler)` for this reason; keep that if you touch it.
- `MatBottomSheet` shows one sheet at a time: opening one closes any other. To link to a policy from inside a sheet, reopen the first sheet when the policy sheet closes, passing its state back in (see `SignInSheetComponent.openPrivacyPolicy()`).
- `@panzoom/panzoom` applies its start position asynchronously, so pass `startX`/`startY` as options instead of calling `pan()` right after creating it. It also sets `overflow: hidden` on the parent unless you pass `overflow: 'visible'`.
- Drawing images from the storage server onto a canvas taints it in the e2e browser. Fetch the blob and use `createImageBitmap` instead.
- On an auth callback page, prefer a hard redirect (`window.location.href`) over `router.navigateByUrl` once a session is detected — Supabase-js strips the token from the URL via a same-document navigation that races with and can cancel an in-flight Angular Router navigation.
