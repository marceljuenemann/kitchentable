# Connections and messaging

**Status: plan, nothing built yet.** This describes the intended schema and sync design for intros, connections and messages. Update it as the pieces are built (and move anything that turns out differently). Profile statuses and the general access rules are in [database.md](database.md).

## Goals

- **Local first:** the app reads and writes a local RxDB database, so it feels instant and copes with spotty connections. Sends queue up offline and go out when the connection is back.
- **Private read state:** whether someone has read a message is never visible to the sender. No read receipts.
- **Few, content-free emails:** an email says that there are new messages, never who from or what they say, and backs off when the user doesn't come back.

## Tables

- `connections`: `id`, `initiator_id`, `recipient_id`, `status` (`pending` | `accepted` | `declined`), `created_at`, `updated_at`. An intro is a `pending` connection whose first message is the intro (PRODUCT.md: an intro message instead of a like). Unique on the pair of users.
- `connection_members`: `connection_id`, `user_id`, `last_read_at` (`not null`, starts as the time the row is created, so the email rule below never sees a null). One row per participant. It's what every other policy checks ("is the caller in this connection?"), and it holds the read state, visible only to its owner.
- `messages`: `id` (uuid generated by the client), `connection_id`, `sender_id`, `body`, `created_at` (set by the server), `updated_at` and `deleted` (both for replication). Indexed on `(connection_id, updated_at)`.
- `profiles.messages_emailed_at`: when the user was last emailed about new messages (see below). A column rather than a table, since clients never touch `profiles` directly anyway.

The client-generated message id makes sending idempotent: a send retried after a dropped connection hits `on conflict do nothing` instead of creating a duplicate.

## Read state

RLS filters rows, not columns, so a read flag on `messages` can't be hidden from the sender with a policy. Column privileges (`grant select (…)`) could, but they break `select *`, which replication uses, and it isn't clear that Realtime respects them. A per-message flag would also mean the recipient updating rows someone else wrote.

Instead, each participant has a watermark, `connection_members.last_read_at`, readable and writable only by that participant (`user_id = auth.uid()`). Opening a conversation sets it to now: one write, however many messages there were. A message is unread for a user if someone else sent it after their `last_read_at`.

## Sync with RxDB

The app has three local collections, mirroring the tables: `connections`, `connection_members` (the user's own rows only) and `messages`. The UI reads and writes only these, so the conversation list, unread badges, accepting an intro and sending all work instantly and offline; replication catches up in the background.

- **Pull:** RxDB reads `connections`, the caller's own `connection_members` rows, and `messages` directly through the REST API, under RLS: a row is visible to members of its connection. It pulls by an `(updated_at, id)` checkpoint, with `updated_at` set by a trigger so clients can't fake it. Deletions are soft (`deleted = true`), so they replicate too.
- **Push:** writes go through procedures, not table inserts, so the rules live in one reviewable place (the same approach as `profiles`):
  - `send_message(id, connection_id, body)`: the sender is `active` or `disabled` (see "Profile status" in database.md), the connection is `accepted`, and the body has a sensible length.
  - `send_intro(id, recipient_id, body)`: creates the `pending` connection, both member rows and the first message; enforces the daily intro limit (PRODUCT.md suggests 3) and that the recipient is `active`.
  - `accept_intro(connection_id)`, `decline_intro(connection_id)`: recipient only.
  - `mark_read(connection_id, read_at)`: sets the caller's `last_read_at` to `read_at`, the time the user read it on their device. It only moves forward and is capped at `now()`. Using the device's time rather than the time of the push matters offline: otherwise messages that arrived on the server between reading and syncing would count as read without the user having seen them.

  RxDB's generic replication (`replicateRxCollection`) takes a custom push handler per collection, which turns each local change into one of these calls:
  - a new message → `send_message`, or `send_intro` if it's the first message of a connection the user started. The client generates the connection's id too and writes it locally, but the server creates the row in `send_intro`, so the `connections` handler ignores new rows. This avoids the message being pushed before its connection exists.
  - a connection's `status` changed → `accept_intro` or `decline_intro`.
  - `last_read_at` changed → `mark_read`.

  Conflicts can't really happen: messages are append-only, only the recipient changes a connection's status, and only the owner writes their member row. If a procedure refuses a change (say, the daily intro limit), the next pull brings back the server's version and the app shows why.

- **Live updates:** a Realtime subscription only tells RxDB to pull now (`RESYNC`); the pull is the only source of data. A missed event just means the next pull catches up.
- **Profiles stay out of RxDB** at first: the other person's name and photo come from a `get_connection_profiles()` procedure and are cached in memory.
- **Local data is per user** and is deleted on sign-out, alongside `UserStorage.onSignOut()`.

## Email notifications

A pg_cron job (like `purge-analytics-events`) runs every 10 minutes and, through `pg_net`, calls a `notify-messages` edge function (like `notify-admin`) for each user who is due an email. The email says "You have new messages on Kitchen Table" and links to the app: no names, no message text.

A user is due an email when:

1. they have an unread message that arrived **after their last email** (no reminders about messages we've already emailed about), and
2. that message is **at least 15 minutes old** (so people chatting in the app aren't emailed), and
3. if they haven't read anything since the last email, enough time has passed since it: at least as long as they had already been away when it was sent, and at least 1 day, at most 30 days.

"Read anything" means their latest `last_read_at` across all their connections. With `read` for that and `emailed` for `messages_emailed_at`, the last condition is:

```sql
read >= emailed
or now() - emailed >= least(greatest(emailed - read, interval '1 day'), interval '30 days')
```

This doubles the wait for each unanswered email without counting them: for someone who was last in the app just before the message came, emails go out after 15 minutes, then 1 day, 2, 4, 8 and 16 days, then every 30 days. Someone who had already been away for a while gets a longer wait after the first email. Reading anything resets it.

One email covers all conversations, which is why the state is per user and not per connection. An opt-out setting can come later.

## Open questions

- **Declined intros:** does the sender see "declined", or does the intro just look unanswered? Not showing it is kinder and reveals less.
- **Deleted users:** their profile stays as a tombstone. Do their sent messages stay visible to the other person, or are they scrubbed?
- **Retention:** keep messages until either participant deletes their account, or for a fixed time?
- **Back-off ceiling:** once the wait reaches 30 days, keep sending monthly, or stop until the user comes back?
- **To check before building:** what RxDB's Supabase replication plugin expects (column names, `select *`), or whether to use the generic replication directly as planned above.
